# Taoist R104 revive timeout review

Read-only review of the sanitized report, final snapshot, and bounded trace. No source, live, process, store, account, or session mutations.

The run completed bootstrap and recorded four successful town revivals before the terminal failure. Successful self revive packets were present at 14:33:07.836 (sequence 86916), 14:45:25.371 (92860), 14:54:09.269 (96735), and 16:03:39.618 (129931). Each was followed by an `ObjectRevived` AOI packet and healthy town state.

The terminal failure is different. At 16:17:02.663 the trace sent `townRevive` (sequence 137355) while the latest authoritative snapshots still showed the Taoist alive in D2031: HP 17 at 16:17:01.942 (sequence 137342), then HP 1 and `dead:false` at 16:17:02.716 (137356) and 16:17:03.689 (137361). The actual self `Death` arrived later at 16:17:04.877 (137367), with `ObjectDied` at 137372 and the final snapshot at 16:17:05.008 showing HP 0/dead in D2031. No later self `Revived`, `UserInformation`, or `UserLocation` town transition appears before the timeout/finalization at 16:17:22.677. The only town-revive command in this final interval was the premature 16:17:02.663 request.

Current lifecycle code is internally consistent with the successful evidence: `protocol-play.mjs:23-30` returns early unless the current self snapshot is dead/HP<=0, requests `townRevive`, waits for the self `Revived` packet through `ProtocolClient.request` (`protocol-client.mjs:142-145`), then requires a healthy world snapshot. The runner’s death recovery call sites are guarded by `playerIsDead`/HP checks (`run-protocol-journey.mjs:1148-1151`, with normal recovery branches around 1296-1322). The trace confirms that the packet name `Revived` is correct for successful self revival; `ObjectRevived` alone is not sufficient.

Assessment: the timeout is real, but this artifact does not show a missing revive packet after a valid terminal death request. It shows a town-revive request issued about 2.2 seconds before the authoritative death, followed by no second request after death. That is the concrete remaining concern: stale/racy recovery dispatch (or an upstream caller invoking `reviveInTown` while the live snapshot was still HP>0), not a justified acceptance of `ObjectRevived` as self revival. Ordinary restart from the persisted state is justified as a bounded recovery attempt because the prior four revive cycles and current lifecycle guards work, but it should be treated as diagnostic until the premature-request path is explained; do not claim the journey is fixed or completed.

## Tightened terminal diagnosis

The immediate trigger is confirmed as a rounded-percent control bug, not stale prior-life state. At 16:17:02.649, `DamageIndicator` for self object `1000` reported damage 16 and `ObjectHealth {objectId:1000, percent:0}` (sequences 137351/137353). The runner sent `townRevive` at sequence 137355, before the next authoritative snapshot. That snapshot at 16:17:02.716 still had `playerHp:1`, self `hp:1`, `dead:false`, map `D2031`; the next at 16:17:03.689 was unchanged. Authoritative `Death`/self zero arrived only at 16:17:04.877 (137367), followed by `ObjectDied` for object 1000 at 137372.

`protocol-observation.mjs:122-131` makes `observedPlayerHp` prefer `playerHealthObservation === 'percent'` over exact `snapshot.playerHp`; percent 0 therefore returns HP 0. `protocol-observation.mjs:263-267` sets that percent mode on `ObjectHealth`. `run-protocol-journey.mjs:1219-1223` then defines `playerIsDead` from this derived HP, and `protocol-play.mjs:23-29` dispatches town revive. This explains the premature request and the later `Timeout waiting for Revived`.

Required regression: with an authoritative self snapshot `{playerHp:1, entity.hp:1, entity.dead:false}` followed by self `ObjectHealth {percent:0}`, assert `observedPlayerHp` remains positive and neither `playerIsDead` nor `reviveInTown` sends `townRevive`; only an authoritative exact zero/dead `Death` or a subsequent exact health snapshot may arm revival. Recheck the existing percent-only behavior for non-self/monster entities separately. An ordinary restart is justified after this guard is corrected or explicitly mitigated; the current R104 timeout should be classified as a confirmed control bug.
