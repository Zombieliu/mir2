## Mail Read/Delete retry correction

The earlier Read/Delete negative-receipt gap is now corrected at the native request lifecycle. Crystal directly enqueues these status commands and has no persistent request lock or negative ACK. Native ReadMail/DeleteMail therefore no longer allocate persistent pending keys. Exact duplicate commands are deduplicated only while undrained; a full queue rejects the new request without evicting another intent. After sending, a fresh user action may retry against unchanged authoritative mail. Existing confirmation and attachment-identity checks still apply. No read/deleted state is predicted and no synthetic ACK or timeout is introduced. Collect/Send retain their correlated pending protections.

Source/backend audit confirms duplicate read is logically idempotent, duplicate delete targets an already-deleted exact ID and returns silently, and durable authenticated character/mail identity plus persistence guards remain in force.
