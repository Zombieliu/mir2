# 生产级完成度评估 — mir2-web3 (Rust) vs Crystal (C#)

> 评估日期: 2026-05-30
> 评估对象: 分支 `claude/optimistic-gates-hMc7O` 的 `mir2-web3` 实现
> 对照基准: Crystal / Legend of Mir 2 (热血传奇2) C# 服务端+客户端引擎

## 方法与可信度声明

- 独立通读了 `apps/simulation/src/runtime/`(战斗/技能/移动/地图/AI/会话/共享 Zone,
  约 6.6 万行非测试代码)、`packages/protocol`、`apps/web` 资源管线,并按模块派只读
  子代理深挖,再亲自抽验了伤害公式、属性体系、封包计数等关键结论。
- **Crystal C# 源已核对**(2026-05-31 更新): `git submodule update --init Crystal`
  可正常拉取 `Suprcode/Crystal`(亦镜像于 `Zombieliu/Crystal`),据此**用真实 C# 源**
  校准了以下数字 —— `Server/MirObjects/Monsters/` 实测 **212 个逐怪 AI 子类**、
  `Server/MirObjects/PlayerObject.cs` **14,682 行**、`MonsterObject.cs` **3,870 行**、
  `Shared/` 21 个 .cs(封包/枚举/Stats)。这把"怪物 AI 是最大缺口"从估计变成了实锤。
- 早前初评时该子模块尚未初始化,本文已据真实源更新;如需逐文件/逐封包 diff 可直接读
  `Crystal/` 工作树。
- 本文的百分比是**生产级 gameplay 深度**口径,**不等于**仓库 `PARITY-TRUTH-AUDIT.md`
  里的 "Candidate 自动化证据" 口径。后者偏宽松(自评 ~90%),本文偏严格。

## 核心结论

**广度/脚手架已经很完整;游戏模拟的深度/保真度才是真正短板。**

| 维度 | 完成度 | 说明 |
| --- | ---: | --- |
| 广度 / 基础设施(协议、封包、资源加载、架构边界) | **~85–95%** | 封包枚举近 1:1,资源管线真实可跑,网关/会话/路由分层清晰 |
| gameplay 模拟深度(战斗数学、怪物 AI、属性引擎、动态世界) | **~30–45%** | 公式被简化、AI 多走通用状态机、世界权威未统一 |
| 生产级多人/运维(共享权威、分片、持久化、分布式) | **~40–50%** | 共享 Zone 骨架是真的,但战斗/AI/NPC 仍 per-session;单进程、无分片 |

## 最影响"能否当生产级在线游戏跑"的硬卡点(按优先级)

1. **世界权威统一进 Zone**: 把战斗/怪物 AI/技能结算/NPC 变更/拾取从 per-session
   提升为单一权威 tick。否则真多人同屏打同一只怪会不一致。**(工作量最大)**
2. **战斗数值引擎重写**: 补 `Random(MinDC~MaxDC)`、AC/MAC 减伤、暴击、完整中毒/元素。
3. **怪物 AI 从通用机扩到逐怪行为**: 决定"手感像不像传奇",缺口最大、最吃量
   (Crystal 实测 212 个子类 vs 此处 ~38)。
4. **持久化归一化 + 并发/事务安全**: 背包/经济入库,去掉单进程串行依赖。
5. **零星资产补齐**(Objects/209、小地图、音效): 工作量小但卡 `/api/scene/crystal` 绿灯。

## 把所有模块推到 90%+ 的工期估算(Opus 4.8 Max 驱动 + Sonnet worker)

> 以下为数量级估算,误差很大;AI 代理在大型、涌现性、多人并发代码库上的吞吐尚无成熟基准,
> 主导风险是**集成/调试时间**而非代码生成时间。

**前提假设**:
- "90%" 按本文严格的 gameplay 深度口径,而非宽松的 Candidate 口径。
- Crystal C# 源码可用作规格(开源,成立)。
- 原版 Crystal 客户端美术/音效资源齐全(资源/地图美术达 90% 的前提,当前部分缺)。
- 连续运行;Opus 4.8 驱动 + 并行 Sonnet worker;复用现有测试/gate 工具链。
- 有人类周期性做验收/审查(项目自评的最终 1:1 需人工视觉/手感验收,代理不能自证)。

**三类工作分别看**:

| 类别 | 内容 | 代理适配度 | 连续墙钟估算 |
| --- | --- | --- | --- |
| A. 代理擅长(机械、Crystal=规格、可并行) | 战斗数值引擎、技能 67→130、怪物 AI 40→200+、属性引擎、封包/NPC脚本深度 | 高(代理强项) | **~2–5 周** |
| B. 代理吃力(设计+并发+迭代调试) | 世界权威统一、持久化归一化+事务、动态地图、多人集成+soak/load+涌现 bug | 中(慢、难并行) | **~6–12 周** |
| C. 代理无法独立闭环(需外部输入/人工) | 原版资产采集、活体 Crystal 逐字节封包对照、人工视觉/手感验收 | 低(非工期问题) | 受外部输入约束,非代理墙钟 |

**结论数字**:
- 若 "90%" = 代码/gameplay 深度且资产齐全: **约 2–4 个月**连续运行,瓶颈在 B 类
  (多人并发调试天然迭代、难并行)。
- 若 **100M token 为硬上限**: 大致够把 A 类(深度移植→90%)做完并显著推进 B 类,但
  **不足以**把世界权威+持久化+soak 全面打到生产 90%。预期 100M 能到"gameplay 深度类
  模块普遍 90%,但多人权威/持久化/运维仍约 60–75% 且未做生产硬化"。全量横扫预计需要
  数百 M token。
- 墙钟受 B 类调试迭代与 C 类外部输入双重制约——**这两项不是加 token 能解决的**。

**建议排期(让上述估算可执行)**:
1. 先做 A 类里"规格清晰、可大规模并行"的移植(怪物 AI、技能效果、战斗公式、属性表)——
   性价比最高、最能体现代理优势。
2. 同步立项 B 类的"世界权威统一"——这是生产门槛,越早越好,因为它会反复影响 A 类成果。
3. 持久化归一化与动态地图在权威统一之上做。
4. C 类(资产/活体对照/人工验收)与人类协作并行推进,不阻塞 A/B 的代码进度。
