# Windows 五分钟更新：资源包与版本切换架构

日期：2026-10-29。状态：架构设计，尚未实现、签名或发布；五分钟目标尚未验收。
线上仍为 [23 / 24 渠道](DUBHE-WALLET-WINDOWS-AUTOUPDATE-20261029.zh-CN.md)。
本轮逐文件 I/O 优化只是未发布的实验，不代替本方案，也不代表已经达标。

## 目标与第一性原理

玩家需要得到完整、一致、可运行的新版本。实现这一点并不要求将每个 PNG、JSON、地图都
变成一个需要独立打开、校验、复制、刷盘、替换和恢复的 Windows 文件。

当前设计把运行时资源粒度、网络分发粒度和安装事务粒度绑定在一起。
应将三者分开：游戏仍按原逻辑路径读取素材，网络按内容包传输，安装按完整版本切换。
根治点是减少文件系统操作的数量，而非仅缩短每次操作。

真实 Candidate28 有 255,069 个载荷文件、1,202,414,057 bytes。
上次仅 checking、preparing、installing 就用了 821.327 秒；即使其他阶段耗时为零也超过五分钟。
staging 另耗 929.551 秒，但其中包含 865 个原文件下载，不能全部归为磁盘耗时。
依据：[原始阶段日志](generated/player-qa/dubhe-wallet-windows-autoupdate-20261029/real-public23-24-last-run.jsonl)、
[实际安装报告](generated/player-qa/dubhe-wallet-windows-autoupdate-20261029/real-legacy-launcher-public-s24.json)。

## 架构决策

采用 **不可变、可随机读取的资源包 + 签名版本清单 + 单个原子版本选择记录**。

```mermaid
flowchart LR
    A[完整资源清单] --> B[复用旧内容 / 打包新增内容]
    B --> C[不可变 packs + 签名 GenerationManifest]
    C --> D[Cloudflare / R2]
    D --> E[断点下载、流式校验、落盘]
    E --> F[原子切换 active-generation]
    F --> G[启动对应 EXE 和同版本 ResourceStore]
    G --> H[直接读取包内素材]
```

资源包是游戏的长期运行格式。安装后保持资源包，不能再将它们展开成几十万个临时文件。
现有 `MIR2PK01` 是整条 gzip 的顺序传输格式，仍要逐项解包，因此不能直接充当随机读取格式。

### 1. 一个资源接口，覆盖全部读取路径

新增 `ResourceStore`，提供 `read`、`open_range`、`exists` 和 `list_prefix`。
生产版使用 `PackStore`；开发环境保留显式的 `LooseStore`。
虚拟路径继续沿用现有 PNG、JSON、字体、声音与地图路径，资源内容逐项保持相同 SHA。

必须同时接入 Bevy AssetReader 和同步原生读取接口。当前不少调用绕过 Bevy：
[assets.rs](../apps/game-client/platform-windows/src/assets.rs) 返回 PathBuf，
[atlas.rs](../apps/game-client/platform-windows/src/atlas.rs)、
[map_parser.rs](../apps/game-client/platform-windows/src/map_parser.rs) 等直接读取文件。
只注册 AssetReader 不构成完整迁移。

Windows 将同一个 store 交给两种适配器；默认 AssetSource 必须在构建 DefaultPlugins/AssetPlugin
之前注册。Web 沿用原入口。灯光存在性和共享音频的 WAV 目录发现同样要迁移；
已内嵌的九语言字体保持原路径，资源缓存键包含 generation，避免切版后读到旧内容。

所有资源存在性、地图 gzip、图集页与元数据、帧、特效、字体、声音读取都要经过同一 store。
原路径语义、全部资源覆盖、九语言、经典画面与职业策略保留；不改变服务器玩法和账号模型。
生产 pack 模式缺失资源时，只能修复签名清单指定的包或明确失败，不能静默回退到未绑定的裸文件下载。

### 2. 增量复用按内容地址，避免全局重排

资源内容以 SHA-256 标识。构建时先查上一份受信索引；已有相同内容直接复用原 pack 引用，
只将新增或改变的内容写入新 pack。未改内容不因路径排序或新文件插入而全部重新打包。
删除资源只改变新版本索引，不就地改写旧包。

初版目标为每包约 32–64 MiB；按稳定逻辑域、路径哈希子桶组织新内容，避免按全体文件重新填满分片。
一个大 ZIP 或每次重排全量资源，会让很小的修改变成全量下载，不能作为日常更新格式。
旧索引只读；发布过程 create-only，新对象永远使用新 digest。

每个 generation 的资源索引唯一绑定 `当前逻辑路径 → 内容 SHA → pack digest + 条目/offset`。
别名或改名可引用旧包的相同内容；删除路径必须从新 generation 索引消失。
`read/exists/list_prefix` 只以该索引决定可见性，不能遍历共享旧包的历史路径来补回已删除资源。
必需 pack 集合必须恰好等于此索引的完整引用闭包。

每个包包含固定版本头和有界索引：逻辑路径、offset、压缩长度、原始长度、内容 SHA、codec。
PNG 等已压缩内容可直接存储；需要压缩的条目或小块必须能独立解码，避免取一帧时解压整包。
offset 溢出、越界/非法重叠、大小写重复路径、超限解压、可执行内容和链接全部拒绝。
包内路径只供资源查找使用，不用于向任意文件系统位置解包。

### 3. 版本清单是唯一事实来源

新的 CMS 签名 `GenerationManifest` 绑定：

- generation ID、单调发布序号、最低 engine 版本、协议和资源 profile；
- EXE、受签默认配置、资源索引的大小与 SHA；
- 完整必需 pack 集合及其 digest、长度、索引 digest、格式版本；
- 对应源码与资源构建来源。

顶层清单列包与索引引用，不再枚举并扫描 25 万个物理文件。
完整逻辑资源索引放在受摘要绑定的索引/包中；解析、总大小、条目数仍设明确硬上限。
新 parser 初版沿用完整资源不超过 300,000 条、总载荷不超过 4 GiB 的边界，
为 pack 数量和索引解码大小另设上限，并在真实构建后固定具体值。
EXE/DLL 继续作为少量独立代码文件，不从资源包执行代码。

### 4. 下载直接形成最终对象

只下载当前版本缺少的 digest，保留受界限的并发、Range 续传与严格 HTTPS 来源规则。
下载时计算完整 SHA，检查大小、索引和清单绑定；最终对象刷盘后，以 digest create-only 发布。
已有包的复用仍需可信校验，不能只信文件名、mtime 或一份可修改的“已验证”标记。
校验后到使用期间以受检句柄和运行期 lease 保护对象，避免校验另一文件、使用被替换文件。

省掉缓存文件到 staging 的再次复制、逐文件备份和十万次 live 替换。
空间预检按“新增唯一包 + 新 EXE + 临时文件 + 余量”计算；旧版本不被覆盖。
单文件落盘本身有成本，Microsoft 也说明频繁调用 FlushFileBuffers 可能低效；
这里通过减少持久化对象数解决，保留关键持久化屏障。
参见 [FlushFileBuffers 官方说明](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)。

### 5. 激活是一次版本选择，不是逐文件覆盖

```text
Mir2Launcher.exe                         # 保持历史 bootstrap 入口
updater/engines/<sha>/                   # 保持受签引擎升级契约
game/                                   # 历史安装和未知个人文件原地保留
objects/packs/<sha>.m2p                  # 不可变资源对象
generations/<manifest-sha>/              # 新 EXE、清单和少量默认配置
state/active-generation.json             # 唯一可变版本选择记录
userdata/                               # 新版明确的本地可写数据；既有 APPDATA 偏好沿用
```

选择记录一次性包含 active、previous accepted、pending health 和 attempt ID。
previous 使用明确的联合类型：已签名 generation 引用，或首次迁移前的已验证 v4 legacy 安装引用。
新 generation 的全部必需对象验证并持久化后，才在安装锁下原子替换这一份记录。
选择记录自身也须先写临时文件并刷盘，再执行同卷原子替换，不能只持久化资源对象。
不要把 active、previous、pending 拆成三个独立写入的指针。
选择记录不是签名权威；启动时仍验证它引用的签名清单、固定派生路径和代码摘要。

切换前崩溃仍使用旧版；切换后只能看到完整新版和待健康确认状态。
新版失败时将选择记录原子切回已验证旧版，不需要恢复十万文件。
最高受签发布序号另行保留，本地受控健康回滚不降低网络防降级水位。

新游戏要报告正确 generation 已挂载、登录界面准备就绪，并真实存活至少 10 秒后才能接受。
`--check-only` 保持 pending。提前退出即使 exit code 为 0 也不能算新版本健康。
当前 [updater.rs](../apps/game-client/windows-updater/src/bin/updater.rs) 的提前成功退出判定需要在新协议中修正。

安装锁延续到游戏生命周期；新 generation 共用 install ID/GameLease，覆盖不同 EXE 路径。
迁移时仍准确检测和排斥旧 R25 EXE，不能缓存“游戏不存在”结果。
运行中 generation、active、previous、pending 和用户目录不得被清理。
远端对象的保留期也必须覆盖仍有效签名发布的引用。

## 旧客户端迁移和发布顺序

1. 先完成新游戏双资源 provider、新引擎双格式支持与离线迁移测试。
2. 在独立、编译固定的新格式渠道上传完整 pack 目标，验证所有不可变对象和签名，再提升其 latest。
3. 最后提升原 v1/v4 渠道的 engine-only 桥；桥继续携带对应原游戏，不将新格式清单交给 C824。
4. 原启动器取得新引擎后，由新引擎进入新格式渠道。根 `game/VERSION.json` 等旧 bootstrap 契约保留。
5. 分别验证真实 R25、当前 C824 用户的完整迁移和原路回滚；全部通过后才扩大发布。

各渠道分配不冲突、严格递增的发布序号；发布桥必须依赖精确的新目标已经公开激活。
R25 的 legacy 渠道和 C824 的 five-class 渠道分别提供 engine-only 桥，并保留各自真实游戏。
新格式目标的序号必须高于所有桥，例如分配桥 `N`、`N+1`，目标 `N+2`，
实际发布时先提升目标 `N+2`，再提升两份桥；否则最高版本水位会将新目标拒绝为降级。
Cloudflare 仅需增加新格式渠道的明确读取 allowlist、对象规则与缓存策略；保留原渠道和 DNS。
不需要启动 Docker，不改游戏服务器、账号、角色或数据库。
历史客户端的引擎桥接和健康确认属于首次迁移成本，必须单列实测，不能用日常更新成绩替代。

## 五分钟是端到端发布门禁

计时从游戏关闭状态下触发更新，到目标版本可交互登录页且真实健康确认成立。
包含校验、下载、解码、持久化、切换和游戏启动；外部审计脚本的重复全盘 hash 单独报告。
真人扫码授权等待属于用户操作，不混作更新器耗时。

| 预算项 | 设计上限 |
| --- | ---: |
| 清单获取和版本发现 | 10 秒 |
| 必需新内容下载 | 180 秒 |
| 内容/索引校验与落盘 | 45 秒 |
| 原子切换和启动至健康登录页 | 45 秒 |
| 余量 | 20 秒 |
| 合计 | 300 秒 |

这是待验证预算，不是已取得的性能数据。下载可与校验重叠，但对外报告完整墙钟，不能相加并发 worker 累计值。
验收档定义为 Windows、SSD、固定安全软件配置、持续有效吞吐至少 60 Mbps；
首版完整目标下载预算控制在约 1.25 GB 内，普通发布另设新增内容预算并在 CI 检查包复用率。
达不到预算的构建不能靠预填目标缓存或仅展示“下载完成”冒充通过。

物理下限必须承认：现有 18 bundles 共 1,010,495,094 bytes，加现有元数据等约 1.077 GB，
即使本地处理为零，五分钟也至少需要约 28.73 Mbps 有效吞吐；
预留本地处理 120 秒则至少约 47.88 Mbps。这是现有格式的大小预算，不是新 pack 的实测体积。
慢网络无法靠本地架构保证全量五分钟；新架构负责去掉当前确定存在的十几分钟本地固定成本。

验收分别覆盖：首次无缓存、R25 大版本迁移、当前版升级、目标缓存为空的日常增量、随机部分缓存与断点重试。
每类至少交错重复三轮，公布每次完整墙钟和传输字节，不能用三轮结果宣称 p95。
逐项比对所有逻辑资源的 size/SHA，覆盖地图、图集、特效、字体、声音、登录语言与经典建角画面。
另做下载中断、空间不足、损坏索引、坏签名、每个激活边界断电/进程中断、提前退出、运行中更新和回滚验证。

实施按依赖顺序交付四个可验收部分：PackStore 与可重复构建格式、全部资源读取迁移、generation 激活与兼容桥、真实端到端五分钟门禁。
它们属于同一架构的必要闭环，不能只完成打包或启动器就宣告解决。
