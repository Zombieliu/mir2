# R16 满包交易本地候选

固定 Crystal `92b4ce4` 在放入报价时腾出背包格，解锁只解除确认。旧 R16 副本要等到确认才腾格；通过普通卸装填满腾出的格子后，解锁需先再腾出一格。测试以预填 40 格的隔离 File 角色开始，后续使用普通交易和装备操作。 [旧版复现](baseline-full-bag.json)

本地候选的十格报价有独立保管。浏览器实测从 40 格放入蜡烛，卸装填回 40 格，解锁保留蜡烛，再穿回装备只腾出原格并取回原编号。取消和双方重登入档保持装备、物品和金币。该次 WebGPU 使用候选 r2。 [满包画面](browser-full-bag.png) · [普通界面操作](browser-full-bag.json)

候选 r4 的两条普通 WebSocket 路径补验满包解锁、对端改价使旧确认失效、精准取回、双方重新确认后各交割一次。满包取消时，原编号物品只生成一封退件邮件，金币退回，双方正常重登入档。运行收据的 `sourceHead` 是启动时所在分支的基点，确切运行包以 `binarySha256` 区分。 [成交](candidate-full-bag.json) · [退件](candidate-overflow.json)

异常重启是合入门槛。仅一方确认时，已持久化的原报价和 17 金币在强制退出、同档启动后仍保持锁定，普通取消无结束回包。另一次在收到显式解锁回包后强制退出，存档仍是原确认态，重启同样锁住。两次对端均未确认，来源档保持，两个测试进程均已关闭。两份异常收据的 `passed` 表示复现成功。 [单方确认](candidate-abrupt-restart.json) · [收到解锁回包后退出](candidate-ack-before-restart.json)

继续用持久化的双方匹配标记区分尚未提交与结算结果未知，前者可恢复，后者保留同一结算身份等待权威结果。交易实现仍为本地候选。真实 PostgreSQL、Windows 窗口和公开发行继续分项验收。
