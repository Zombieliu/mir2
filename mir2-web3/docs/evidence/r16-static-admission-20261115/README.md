## 先追查原来的 97 次 504

原公开流程留下 97 次错误，归并为 **92 个地址**。其中 **41 个地址后来有页面侧 200／finished 记录，51 个未观察到后续成功**。六字体的最终完整 SHA 和指定 113 项另有原始证明；不能用它们推导所有面板图片恢复，也不能将页面 200 一概当成逐张图片 SHA 验收。[逐地址记录与原始文件摘要](resource-path-audit.json)。

在原选定的来源内，静态记录 615 行、瀑布记录 1086 行、均未截断；其中观察到的上游图片请求峰值为 123，许多读取在响应头前以 `net::ERR_ABORTED` 结束。另核实原 `perf-probe.mjs` 只给瀑布观察器传入应用源和当前主素材源，**五个配置中的后备路径前缀未纳入上游图片采集**。所以这不是完整来源链的归因证据，不能断言历史上每个 504 都由同一个原因产生。下一次公开回放须显式传入配置内全部七个许可来源，不放宽到任意地址，也不倒填旧记录。

## 读取排队修复

- 普通静态资源最多六个逻辑读取同时等头；排队阶段不启动来源的 7 秒计时，实际获得名额后仍沿用每来源原等待与重试规则。
- 一个已进入读取的资源连续尝试原有来源，不因换源重排到其他图片后面。排队时冻结来源列表，后来的 Worker 配置不会让旧缓存填充读取新版本素材。
- 沿用清单／hint 的 critical、runtime、background 顺序，同一档先进先出；临近分发时重新读取 hint，允许将等待中的核心 HUD 素材提前。
- 普通图片拿到有效响应头即释放名额，正文继续流式交给消费者及缓存；不改成全图缓冲。完整字体仍独立使用两个完整正文名额，场景／协议／运行包路径不加入图片队列。
- 共享消费者、完整缓存、取消排队、真实 404 负缓存及瞬时失败规则保留。源码和构建输入见 [source-inputs.json](source-inputs.json)。

真实 Chrome 使用相同的本机 HTTP/1.1 条件、72 个同时请求的图片地址、一个重复消费者及两套原版完整 CJK 字体；每张夹具图片故意使用同一份原版 PNG，响应头统一延迟 1100 ms，Worker 原 7000 ms 限制保持。

## 进度不能提前宣布失败或完成

此前只要 `prewarmFailed > 0` 就显示“失败”，即使同一资源包仍在加载或进行有界恢复；失败次数又被加到完成数中，使 110 成功／3 待恢复也能显示 100%。现在 UI 仅将完整成功结果算入已缓存进度：加载未完显示“加载中”，恢复阶段显示“重试中”，110/113 为 97%；重试结束仍有缺失才显示失败。全部完成后隐藏面板，后续资源波次可以重新出现。

诊断计数、失败历史和实际恢复队列不改写。面板随当前页面语言提供简中、繁中、英文、葡语、俄语、印地语、印尼语、越南语、泰语及阿语；阿语使用 RTL。实际组件的 40 个语言／状态组合经 React 渲染及 Chrome 实拍，30 个未完成面板可见，10 个完成状态由调用方隐藏，无横向溢出。[十语原组件画面](progress-panels.png) · [浏览器检查](progress-visual.json)。这不是其余游戏文案或 Windows 像素对齐完成。
