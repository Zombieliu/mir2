# R16 暂存报价解锁

固定 Crystal `92b4ce4` 的 `PlayerObject.TradeConfirm(false)` 只解除发送者的锁定，继续保留交易。原 R16 双 WebSocket 实测关闭两方并退款。旧副本回包还把木剑的旧式编号重新分配。首轮核对误要求该编号保持，后续按实际退回编号确认物品、钱包与重登入档。 [旧版回执](baseline-wire.json) · [旧版包序](baseline-wire-trace.json)

Gateway 在同一 Zone 锁内恢复发送者尚未匹配的报价，核对原交易标识、双方及暂存物品身份。全部物品能放回报价引用的背包格时才恢复可编辑，冻结金币保持，发一个 `TradeCancel { unlock: true }`。解锁和对端确认共用 Zone 锁下的报价。已被匹配的报价仍由既有成交及退款路径处理。旧式跨网格的编号可保留，背包重复编号或其他持有中的资产编号会阻止恢复。 [构建与源指纹](candidate-build.json)

普通 File WebSocket 上，原发件人解锁两次，物品身份、报价和冻结金币保持。取回并再次放入后，对端单独确认无法成交。发件人再次确认才各交付一次物品和金币，双方普通注销重登的资产一致。两个普通浏览器也完成走位、邀请、接受、放入、报价、确认、解锁、取回、再放入、成交、重登。双方最终 922／778 金币，合计 1700。页面与网络错误为零，最终 File 钱包和背包逐格一致，两端无残留交易。 [协议](candidate-wire.json) · [包序](candidate-wire-trace.json) · [浏览器](browser.json) · [恢复后界面](editable-offer.png) · [落盘](disk.json) · [停止](shutdown.json)

Windows 窗口逻辑在收到权威解锁回包后才恢复编辑。失败时保留锁定并允许重试。背包格不够时服务端保留整笔暂存，空出足够格位后可再次解锁。Crystal 的独立交易格在满包时仍可解锁。对端已经确认后由另一方直接修改报价、旧编号 0 的 Native 投影、实体 Windows 窗口与真实 PostgreSQL 继续单列。

限定回归通过 Gateway 64 项、Simulation 77 项、Native Bevy 交易窗口 45 项与投影 9 项、Web 15 项。Gateway 的三个条件 PostgreSQL 用例未接库。首轮带调试符号的链接因磁盘空间中断，改用独立目录的无符号开发构建完成。首轮回归识别出旧档跨网格编号可重合，并按实档规则修正。满包测试以 40 个背包格和 6 个药品快捷格复验，覆盖暂存原样保留、同背包编号冲突拒绝和后续完整恢复。
