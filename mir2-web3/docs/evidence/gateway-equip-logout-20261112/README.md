## 已确认的原因

- v8 的 actor 27 第三次穿装备，实际回包耗时 **16,649.9042 ms**，超过原来的
  15 秒预算。服务端 connection 229 的同次命令排队 **14,387 ms**、执行
  **2,116 ms**。前一次穿装备虽然已经回包，后续 flush 仍持续 15,732 ms，
  其中 save 持续 14,409 ms，阻塞了同连接的下一次操作。
- 上述 14,409 ms 存档等待区间内，经验准入持有 AccountStore 的慢事件区间并集为
  **12,558.939 ms（87.1604%）**，共 383 段。最后实际存档事务持锁只有
  34.432 ms。日志查询覆盖 50 秒、11,545 条慢事件，未因条数上限截断。
- 个人 runtime tick、穿装备、退出的经验上下文会反复重建所有在线角色的状态。
  100 个角色的回归测试观察到一次个人调用做 **101 次** rebase。
  修复后仅新鲜重建本人及最多两个当前相关角色，同一测试为 **3 次**。
  保留 AccountStore → Zone 的权威锁顺序；世界死亡结算及全员重建路径保持原有语义。
- 这批 100 个账号的存档 JSON 每个为 2,280 字节，均低于已有 64 KiB 解析缓存门槛。
  因此没有上调缓存门槛，也没有修改 PostgreSQL 新鲜度或源刷新锁来规避问题。
- 另有独立的 WebSocket 关闭回包问题：收到 Close 后自动回复仍在发送队列，旧读取端
  直接结束。真实环回测试先复现 `ResetWithoutClosingHandshake`，修复为在受控的
  1 秒关闭回包时间内 flush，并保留现有发送取消屏障。正常退出存档与 LeaveZone 顺序不变。

v8 的 13 个 LogOut 回包超时与 1 个 Close 握手超时分别保留为失败。穿装备期间的
KeepAlive 正常，只能证明该次装备等待没有整连接停收；不能外推到已经停止心跳的退出阶段。

不是硬件实测极限；此前 100 人穿装等待的短区间，主机网卡平均约 0.935 Mbps、峰值
1.764 Mbps，不能把那次超时直接归因于 30 Mbps 带宽。该网卡数字包含其他服务/VPN，
也不等于供应商实际整形上限的验证。

真实测量为准，不把本地原版的 1,000 人数字作为当前云机容量承诺。
