## 确认的两个机制

1. 原 pending 超过 3 秒会丢掉自动路线的执行队列，迟到回包不恢复队列。现在只对仍有有效所属目标的任务／大地图／新移动路线保留一个在途动作，最多等 8 秒；不重复发步。手动替换、失焦、断线、换图和目标变化仍立即撤销；达到期限停止路线并用十语提示，迟到回包不能重启旧路线。手动移动原 3 秒规则保留。
2. 真正造成此次任务路线首步停顿的方向错误已被实际浏览器诊断确认：执行器给出小写 `upright`，移动控制器和 Page 方向运算使用 `UpRight`。实际发 run 后，服务器在 10 毫秒左右合法降级到 `(289,615)`，客户端却将它判为位置纠正、清掉队列。记录中 `ack=1`、`pendingTimeout=0`、`snapshot=0`，所以该次失败不能归因于超时。执行器现统一输出八个标准方向，任务与大地图寻路共用此修复；Gateway 本来就按不区分大小写解析，不改变服务端规则。

修前后同一真实路线／控制器组合由 `correction` 变为 `confirmed`，保留正常偏离路线纠正。见 [原失败与组合回归](regression.json)。此前 [目的坐标／完整碰撞／右键修复](../r16-quest-navigation-20261113/README.md) 已发布并保留。
