# R16 确认后加价与交易邀请

对照 `6c55c05aae` 的已提交 Windows R16 和固定 Crystal `92b4ce4ab`。Native 交易窗口允许已确认的玩家打开金币金额框。Crystal 服务端先清除双方确认，再检查金额。有效请求按增量扣款并将累计报价发给对方。零金币或超过余额只解除确认。

旧 Web 物理点击已确认一方的金币按钮时不出金额框。旧网关收到同一条普通 `TradeGold(11)` 也直接忽略，对端随后能按旧报价成交。两个复现均使用同一份比奇 File 存档副本，记录普通登录、成交和同角重登。

网关使用撮合的同一把 Zone 锁撤回尚未匹配的准备状态，保留物品和已冻结金币。若另一方已取得报价进行结算，改价不再进入扣款路径。已确认一方收到已有的 `TradeCancel { unlock: true }`，有效加价随后收到一次 `LoseGold`。对端仅收到新的累计报价。Web 金币入口在当前角色、场景、交易身份和余额均有效时开放，确认后的物品格仍由原有锁定控制。

普通 File 双开在冻结 137／59 后确认，再直接追加 11。一次扣款，报价更新为 148／59，原物仍在独立报价格。对端单独确认未成交，双方重新确认后钱包为 911／789，原物各入账一次，重登和落盘一致。另以普通协议发送 0 和 642，后者超过当时 641 的余额。两次均解除发送者的确认，原报价、余额和物品保持，且无新报价和成交。

交易邀请复用 Crystal 的 System Chat。普通双账号验证站位错误提示、30 ms 内重发的静默、对方关闭交易、已有邀请、主动拒绝和自己已在交易中的提示。两秒后可正常重邀，接受和取消后双方资产与重登一致。没有新增回包类型。第一次探针把现有英文拒绝文案写错，保留记录并按实际源文案重试。

Gateway 交易回归 73 项，Simulation 交易回归 80 项。隔离 PostgreSQL 16.15 验证准备报价、迟到提交和已成交待投递的 3 项用例。Web 窗口与 Page 136 项、发包顺序 66 项、适配器 508 组及类型检查通过。
