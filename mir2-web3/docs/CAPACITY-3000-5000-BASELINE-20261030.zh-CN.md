# 3000–5000 CCU 容量基线与扩容方案（2026-10-30）

**目前尚未测出单机 CCU 上限，也没有证据证明已支持 3000 或 5000 人。** 当前共享服务器为 4 vCPU、标称 8 GB 内存，磁盘只剩约 620 MiB；它只能做受限诊断，3000–5000 人测试应转到独立服务器。把连接数配置调到 5000，不等于游戏能承载 5000 人。

本轮对 e824 真实服务端执行了两次有界诊断：专用 PostgreSQL 数据库、专用 Redis 实例，Gateway 限额 **1 CPU / 512 MiB**，PostgreSQL 主进程仍与原服共享。**两次均有 2 个正常认证的客户端通过约 60 秒移动、AOI 互见和聊天；两次整轮均未通过。** 首轮因监控 32 MiB 配额 OOM 中断；仅修正监控资源后的 r2，后续窗口出现超过 2 秒的响应超时，触发严格超时门限。测试已停止，未再重跑；未验收战斗、存档重登、长时稳定或容量上限。

**用户随后确认最终负载：3000–5000 人全部持续战斗，分布多张地图。** 3000 与 5000 均按全员战斗目标档记录，不以在线挂机或仅 500 人战斗替代。本页下方方案据此更新；已归档证据中的“5000 分布待定”属于确认前的历史状态，不改写原证据。

### r2 实测结果：整轮未通过

- 运行时间为 2026-10-29 **20:31:29.797–20:33:50.505 UTC**。同两个普通账号登录进服，未重新注册；原 4 次登录记录完整保留，累计 6 次。
- 独立测量阶段 **60.079 秒通过**：AOI 120/120，Run p95 279 ms、Walk p95 182 ms、Chat p95 140 ms，timeout/correction 均为 0。后续观察仅完成 **55.129 秒**。
- 首个失败连续窗口实际为 **60.496 秒**，横跨测量末段与后续观察，不含入场/settle；其中一名角色超时率 **1/80 = 1.25%**，未达到严格低于 1% 的门限。活动量、时延分位、扇出与 native 完成率均通过，不可将整轮记为通过。出现约 2019 ms 的 Run 超时；根因尚未定位。
- 两次正常登出收到成功回执，随后实际连接、会话、重连租约及在途请求均归零。续连与存档重登因失败跳过，不能称持久化闭环已验收。
- 测量阶段的 30 个去重资源样本覆盖 58.010 秒：Gateway CPU 增量 1.40 秒，平均约 0.024 核；该采样范围没有新增 cgroup throttle。后续 26 个样本覆盖 52.010 秒；cgroup memory.current 峰值 94,425,088 B、进程 RSS 峰值 162,525,184 B，Gateway OOM kill 为 0。两种内存口径不能相加。它们不证明不存在瞬时排队，也不能据此归因超时或线性外推人数。
- 原测试服、原正式服与 Caddy 保持原 PID；原 TEST health 仍为 e824、PostgreSQL/Redis healthy。仅本轮 Gateway/Redis 正常停止。监控主程序退出 0，但其停止钩子重复停止已回收的临时 unit，返回 5，最终 failed 状态保留；此清理缺陷须修复，不能宣称全部运维检查通过。

见 [r2 公开摘要](evidence/capacity-3000-5000-20261030/RUNTIME-SUMMARY-R2.json)、[分窗口资源](evidence/capacity-3000-5000-20261030/RESOURCE-SUMMARY-R2.json) 与 [停止及原服健康](evidence/capacity-3000-5000-20261030/FINAL-OPERATIONS.json)。本次从 Windows 通过私有 SSH 转发发送正常客户端协议，时延包含发生器及转发路径；不是公网直连/TLS 的容量结论，也不是原生 Windows 界面验收。

## 2. 当前服务器规格与测试边界

2026-10-29 20:02:50 UTC 的只读实测基线如下，后续剩余资源会变化：

| 资源 | 真实观测 |
| --- | --- |
| CPU | 4 个逻辑 vCPU，KVM，Intel Broadwell；不是独享裸机保证 |
| 内存 | Linux 可见约 7.75 GiB，available 约 1.45 GiB，无 swap |
| 磁盘 | 根盘与 PostgreSQL、测试服共用分区；剩余 649,592,832 B，约 620 MiB |
| PostgreSQL | max_connections=100；当时共 19 条连接；与既有服务共享数据库实例 |
| 网络 | 未取得可保证的带宽上限；网卡累计字节和未知速率不代表云带宽规格 |
| 现有负载 | 同机已有正式服务、测试服务、钱包、PostgreSQL、Redis 等 |

[原始主机基线](evidence/capacity-3000-5000-20261030/HOST-BASELINE.json) 有时间戳和进程/cgroup 口径。隔离 pilot 新建了自己的数据库、Redis、状态及恢复目录，并限制 Gateway 为 1 CPU / 512 MiB；Redis 与 watchdog 另有明确小额度，不能写成全部组件总共只用了 512 MiB。它们仍共享物理 CPU、磁盘和 PostgreSQL，不能称为完全独立的服务器容量测试。

本次配置另外固定为：Tokio worker=1，AccountStore 与 ChannelIdentity 的 PG pool 各为 2，专用数据库角色连接上限 12；Redis 为 0.1 CPU / 32 MiB；r2 watchdog 为 0.1 CPU / 128 MiB。独立实例 active session/WS 准入上限为 128/160，实际只进服 2 人。求购链上任务、USDC/Stripe 收费及 spectator/AI live 等附加模块关闭，保留正常认证、PG、Redis和游戏协议。该配置不同于公开 TEST 的完整运行配置；不能把本次资源采样当作全部功能同时运行的容量。

剩余约 600 MiB 空间容不下 5000 人的准备、WAL、运行日志、快照和恢复证据；提高人数前应换独立资源，不能删除旧备份凑空间，也不能挤占原服。当前许可范围是小诊断，不是直接在共享机上跑 3000/5000 或两小时 soak。

## 3. 架构现在可以做什么

**建议先按地图/Zone 扩容，再处理单张热点地图。** 现有实现已有可复用基础，但还不是加机器就自动扩容的完整系统。

| 能力 | 当前实现 | 对容量的含义 |
| --- | --- | --- |
| 共享世界单写 | 同 execution Zone 的共享状态受互斥锁保护；每 Zone 有独立 owner 线程、受限移动入口 | 保持移动、占格、AOI 与战斗一致；同一个热点 Zone 的写操作仍会排队 |
| 多地图多核 | ZoneManager 至少有 4 个运行地图时，使用持久 ComputeTaskPool 并行 tick，按固定顺序合并输出 | 多地图已经可以使用多核；无需等动态 Cell 才开始测。不能据此说同一地图会自动用满所有核 |
| 地图分组与独立节拍 | 有 single/per_map 与 JSON 地图组、tick 配置，正常 bootstrap 已接入；默认 single | 可把不同地图放到独立执行域；实际部署配置及收益必须记录并测试 |
| 跨机模拟 | 已有独立 zone_host、正常会话 RPC、owner fencing、复制/切换相关组件 | 能复用来建设多 Gateway、多模拟机；本轮尚未完成多机容量与故障验收 |
| 加机放置 | 静态 ACTIVE_ADDRS 按 Zone 哈希取模选 host；可选 finalized placement 控制面 | 改 host 数量会重映射部分 Zone，需要有状态迁移/复制/交接；不是无损自动扩容 |
| 热图分线 | 有按人数/affinity 分线与空线回收；scheduler 状态是进程内 | 分线会分开互相可见的世界；不能把不同线相加说成同一战场人数，多 Gateway 也需统一调度策略 |
| 空间 Cell | 有 64 tile Cell 坐标与分区合同，但全部 Cell 仍属于 partition 0，非零 partition 被拒绝 | 固定 Cell 独立 writer、动态拆分/合并、跨 Cell 战斗权威交接均未实现 |

主要源码入口：[多地图 tick](../apps/simulation/src/runtime/zone/manager.rs#L1388)、[Zone 单写与线程](../apps/gateway/src/routing.rs#L10178)、[拓扑](../apps/gateway/src/topology.rs#L55)、[正常会话 RPC 选择](../apps/gateway/src/session.rs#L1633)、[zone_host](../apps/gateway/src/bin/zone_host.rs#L43)、[host 哈希选择](../apps/gateway/src/zone_rpc.rs#L7747)、[当前 Cell 合同](../apps/simulation/src/runtime/zone/partition.rs#L1)。

**5000 全服在线、分散到多张地图**与**5000 人在同一张地图/同屏战斗**是不同目标。同图 AOI、技能效果与怪物密度可能先达到单写、扇出或网络瓶颈；目前不能承诺同地图 5000 人。跨机验收也必须包括实际同世界交互与切换，不能只把两个互不交互的地图各跑一遍。

## 4. 扩容前要量清的主要瓶颈

1. **AccountStore 串行段。** 当前事务持全进程 persist mutex 与完整 store mutex，复制完整 AccountStore，再等待 PostgreSQL 提交后发布。数据库有 scoped mutation、行锁和版本 CAS，但增加 PG 连接池不能消除这一段。应先测 PersistWait、StoreWait、StoreHeld 与提交时间，再按账号/领域缩小快照和锁范围，保留跨账号交易的一致性。[源码](../apps/simulation/src/config.rs#L5310)
2. **远端 RPC 每会话线程。** live outbound 为每个 session 启动 OS polling 线程，空闲周期 20–100 ms；Host 每条 TCP 连接也有线程。已有共享连接池不能消除每会话 poller。3000–5000 档应实测线程数、RSS、上下文切换和 poll QPS，必要时改为按 host 多路复用或推送。[源码](../apps/gateway/src/zone_rpc.rs#L2435)
3. **Redis 与跨 Gateway 状态。** 缓存操作当前每次建立同步 TCP；重连的真实 GatewaySession、广播与分线部分状态仍在进程内。需要验证跨 Gateway 路由、消息、身份防重放与故障恢复，不能只看到 PG/Redis 在线就宣称入口无状态。[缓存](../apps/gateway/src/cache.rs#L1584)、[重连](../apps/gateway/src/web.rs#L937)
4. **同图扇出与共享资源。** AOI 格子减少候选搜索，不会免除真正接收者的编码、发包和技能计算。CPU 总平均低也可能存在单核、锁、磁盘或 PG 排队瓶颈；需要逐核和因果阶段证据。

生产类 Web 默认 active session 512、WS 2048；ZoneHost 默认 session 4096、连接 64。这些只是准入配置，不是测得的承载人数。调大前要同时明确连接、线程、文件句柄、保存、恢复与数据库预算。[Web 配置](../apps/gateway/src/web.rs#L103)、[Host 配置](../apps/gateway/src/zone_rpc.rs#L61)

## 5. 3000/5000 人怎么验收

最终活动比例已确定为 **3000–5000 人全员持续战斗、多地图**，尚未运行。仍须冻结具体地图、战斗组位置、职业/技能、准备方式、入口、资源与停止条件；分散地图、热点地图和同屏密度分别报告。此前 500 全战斗仍为中间档，不能代替最终 3000/5000 档。

| 阶段 | 拟议执行 | 可报告的结论 |
| --- | --- | --- |
| 当前隔离诊断 | 2 人 r2 已失败停止；不在同样条件下加人或重跑 | 保留首次超时证据，不能得出单机上限 |
| 独立环境预检 | 固定 binary/内容/技能/地图布局、正常鉴权、PG/Redis持久化、发生器与资源配额 | 具备开始测试的条件，不是人数通过 |
| 快速阶梯 | 2、10、25、50、100、250、500、1000、2000、3000、5000；每档约 15 秒稳定准备 + 60 秒测量 | 仅短测；第一档负载无效或失败立即停止升级 |
| 资格测试 | 最高实际绿档至少 300 秒、5 个完整分钟窗 | 只证明该人数、负载和规格的资格点；不推断更高人数 |
| 长时观察 | 资格通过后，选一个目标点持续 7200 秒 | 限本次确切负载的两小时稳定性 |
| 恢复验收 | 重连/旧票拒绝、正常退出、存档回读、Gateway/Host 故障与 N+1 | 恢复与资产一致性；恢复时间单独计，不藏进稳定窗口 |

正常注册/登录入口的实际预算必须计入时间。现有大规模入口与账号准备仍需补齐目标人数支持；不能虚构一个已可用的 5000 CLI，也不能清认证账本、伪造出口或绕过限流缩短等待。准入、准备、warmup、测量、soak、恢复、drain 分列真实墙钟，避免再无边界反复跑。

现有独立 PvP stress 入口人数上限为 500，fixture 限定地图 `0`；每个进程都要求先检查服务器排空、使用自己的登录账本及测量起点。并行启动多份不会自动产生一个合格的 5000 人结果。下一步需要统一 controller：按地图分配完整战斗组、按真实认证来源共享持久化准入预算、一次排空预检、同一测量窗口以及失败传播；每个 worker 和每名 fighter 的缺失、超时与死亡均计入全局结果。预置账号/补给只属于服务器负载 fixture，不冒充普通玩家养成验收。

关键验收口径沿用已有合同，冻结后逐名角色、逐完整分钟统计：

- 每名 fighter 每分钟至少 18 次真实 launched、12 次正伤害共享 HP 见证，native 完成率至少 95%；ACK 成功不代替对方看见 HP 变化。
- 移动 p95≤750 ms，聊天 p95≤1000 ms；PvP 相关攻击 ACK p95≤900 ms、正伤害 HP 见证 p95≤1000 ms；timeout 严格低于 1%，correction/notLaunched 各≤5%。
- 保持真实 AOI/占格、冷却、伤害、怪物和经济规则；不重叠占格、不缩 AOI、不删效果抬分；不得用正常客户端可调用的 QA/管理员命令补负载。
- 金币守恒、原装备实例唯一归属、最终 Zone 位置保存、恢复无未决；每人负载未达标、发生器跟不上、监控失效或资源保护停止，都不能记为服务端容量通过。
- 记录 CPU 配额/throttle/逐核、内存峰值与 300 秒 warmup 后斜率、PG 锁/提交/WAL、Redis、实际 wire/PPS/突发/重传、磁盘增长和发生器延迟。`zone_metrics` 的 p99 是桶上界，`complete=false` 或无样本不能验收。

完整阈值与待冻结项见 [测量合同](evidence/capacity-3000-5000-20261030/benchmark-contract.md)。合同状态仍为草稿；当前多地图并行已经实现，不应把“未来 Cell 调度”误写成所有多核测试的前置条件。

## 6. 规格如何选，怎么算

**可以把独立 16 vCPU / 64 GiB 作为候选起测规格，不能称为支持 5000 人的推荐保证。** 它只是实验起点，需记录 CPU 型号、实际 cgroup 配额、云盘时延/IOPS 和可保证带宽；PG、Redis、发生器分别列预算。若共机，则它们也必须计入这 16/64 的总预算；若分机，则额外资源必须明列，不能隐含免费。发生器应与被测世界分开，避免自己先饱和。

以下公式用于从已测结果选择下一次实验，不是把两人线性外推到 5000：

| 资源/能力 | 计算方法与限制 |
| --- | --- |
| CPU 使用 | `平均占用核数 = Δ进程 CPU 秒 / Δ真实秒`；同时看单核、throttle、锁等待。候选可预留约 30% 余量，但串行段不随 vCPU 线性扩展 |
| 内存 | `需求 = 基础常驻 + 实测人口/实体/密度增量 + inflight/快照峰值 + PG/Redis + 安全余量`；增量必须在目标密度实测，短测不能证明无泄漏 |
| 带宽 | `实际 Mbps = Δwire 字节 × 8 / 秒 / 1,000,000`；再核对 p95/p99 突发、PPS、重传、TLS 与跨 host 流量，不能拿编码长度或 localhost 代替公网 |
| 存储 | `预留 = DB + WAL 峰值 + 日志/证据增长率×墙钟 + 快照 + 回退空间`；还要满足实际 fsync/IO 延迟，不只看磁盘总 GB |
| 全战斗最低吞吐 | `launched/s ≥ N×18/60`，`正伤害见证/s ≥ N×12/60`；500 人分别为 150/100，3000 为 900/600，5000 为 1500/1000，仅是合同算术 |
| 多机容量 | `全服 CCU = 同时在世界中活跃的唯一角色数`；仅在归属唯一时才可加总各 Zone 实际人数，还受共享 PG、入口、网络、热点分布与故障余量限制；不能相加配置上限或未验证的分片 |

测试结果应写成：“在明确规格、硬配额、地图/技能分布与时长下，实际 N 人通过这些门槛。”只有短测就写短测，未测到失败上档就写“上限未知”。正式安全容量还要保留余量与故障恢复能力，不能以资源全部占满作为上线目标。
