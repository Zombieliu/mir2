# Personal procurement v1 chain boundary

This independent package uses Dubhe commit `04700a9a13e6f279be3709e84bf4ad24b4349af3` and Sui framework commit `3c0f387ebb40b8be292d3b7bd3f5bee8ad226d33` (`mainnet-v1.68.1`). The SDK is exact `@0xobelisk/sui-client@2.0.0` with its own `@mysten/sui@1.35.0`, isolated from the web app and existing mining package. Network I/O uses a separate exact `@mysten/sui-modern` alias for `@mysten/sui@2.16.2` and its gRPC API. Dubhe's obsolete JSON-RPC transport is never used. `UPSTREAM.json` records the real reused APIs. The Dubhe Apache-2.0 license applies to upstream code.

The game server is a trusted asset custodian and identity/condition verifier. Contracts cannot inspect the game database or force a stopped server to deliver. Gold, points and full equipment instances stay in the server database. No asset token, equipment NFT, USDC payment or Marketplace sale is used. Template `245` is the original manifest's HalfMoon/井中月 equipment template; matching by translated display name is forbidden.

## Actual Dubhe integration

`dubhe.config.ts` describes real per-order `ObjectStorage<Order>` fields. `create_order` calls `create_and_share_typed_object`, which registers one unique order entity ID in `DappStorage` and emits `Dubhe_Object_Created`. All field writes use `dapp_system::set_object_field`, producing `Dubhe_Object_SetField` for the existing object indexer tables. Read-only DappStorage version guards are applied on subsequent operations. The generated constructor's lifecycle is deliberately preserved: creation returns no object and takes no initial values, so publication needs **two transactions**, creation and activation. Only activation confirmation permits advertising the order or consuming reserved service quota. A created object with no `status` is not an open order.

Creation mutates the DApp registry once; fill/cancel/expire/revoke mutate only the relevant order and read the DApp/config objects. Separate orders have no common mutable settlement object. Initial deployment/genesis and rare configuration changes are separate costs. There is one contract deployment, not a new deployment per player or order.

The supplied handwritten system is the authoritative business policy; the schema declaration is not a claim that running codegen alone provides custody or reliability. Upstream `generateToml` currently emits stale Sui/tag dependencies, so do not overwrite the pinned Move manifest with it.

## Authorization and proof fence

Frozen `IntentV1` and `OracleProofV1` BCS field order is in `sources/intent.move` and `service/canonical.mjs`; `fixtures/intent-v1.json` is the shared Rust/Node/Move test vector. JSON byte fields are canonical lower-case `0x` hex; u64 values are decimal strings. Actor and Oracle use raw Ed25519 signatures over `SHA256(BCS(struct))`, with distinct domain strings. This is not a Sui personal-message signature and not a blanket authorization from a login wallet.

A player explicitly confirms a displayed quote using a short-lived purpose key bound by the server to the current authenticated game session and account reference. The Oracle separately attests that binding and the actual database lock. The contract verifies both signatures, all domain fields, terms, quantities, deadlines and the current proof fence. A fresh authenticated confirmation key may cancel an order after a client restart; it still requires the buyer reference and a new valid Oracle attestation. Oracle compromise remains a disclosed trust risk.

An order has one terminal decision: FILLED, CANCELLED or EXPIRED. Sui serializes competing writes to that order. A signed fill proof remains a live asset liability until a confirmed terminal result, a confirmed higher fence/key revocation, or a **confirmed on-chain Clock** beyond its deadline makes it unexecutable. Local time or network timeout is never sufficient. `revoke_fence` is an audited on-chain action, not an unaudited database edit. Publication disable/pause blocks new creation while existing activate/settle/cancel/expire/revoke remain available.

## Worker driver

Run `node service/driver.mjs`; pass one JSON request on stdin. It emits one `{ok,result}` or `{ok:false,error,unknown:true}` line. Protocol version is 1. Operations: `build`, `submitExact`, `queryFinality`, `queryOrder`, `replayEvents`, `readClock`.

Every request supplies explicit configuration: `enabled`, `network` (`testnet` or loopback `localnet`), `environmentTag:"isolated-test"`, `fullnodeUrl` (gRPC endpoint), `chainIdentifier` (the standard first four genesis-digest bytes in hex), `networkHash` (`SHA256(UTF8 chainIdentifier)`), `packageId`, `frameworkPackageId`, `dappStorageId`, `configId`, `oraclePublicKey`, `oracleKeyId`, `gasBudgetMist`, `maxGasBudgetMist`, `dailyGasBudgetMist`. Pin the full base58 `genesisDigest` as well. `startCheckpoint` must be the deployment checkpoint for initial gap-free replay; it never defaults to the current head. Optional `eventGraphqlUrl` selects a test-network HTTPS index endpoint; the testnet default is the official `https://graphql.testnet.sui.io/graphql`. IDs/keys are 32-byte hex, all u64 values strings. RPC chain ID and real package/config/storage object types and verifier fields are checked before use. Mainnet and implicit signing defaults are rejected.

`build.payload` has `action` (`create`, `activate`, `fill`, `cancel`, `expire`, `revoke`), `intent`, unsigned `proof`, `actorSignature`, and (except creation) `orderObjectId`. Activation additionally requires `conditionsBcs`: canonical `0x` bytes from the shared `EquipmentConditions.canonical_bcs()` (u16 current durability, u16 max durability, sorted vector of u8/i32 predicates). Its SHA256 must equal the authorized condition hash. These bytes are stored on-chain so the conditions can be recovered independently of the game DB. Expire needs no intent; revoke uses `orderId`, `nextFence`, `validUntilMs`, `nonce`. Explicit environment secrets `MIR2_PROCUREMENT_SUI_SECRET_KEY` and `MIR2_PROCUREMENT_ORACLE_SECRET_HEX` are required before constructing Dubhe. There is no automatic key generation. Build returns exact base64 `transactionBytes`, `signatures`, `digest`, proof/signature and gas budget **without sending**. The owner must durably commit that exact output before calling `submitExact`.

`submitExact.payload` is the saved bytes/signatures/digest. It rechecks digest, signer, target whitelist, configured shared objects and budget. `MIR2_PROCUREMENT_GAS_LEDGER` must name an absolute durable file; digest-idempotent maximum gas reservations are fsynced before sending, with a daily cap. A stale `.lock` fails closed: stop workers, reconcile outstanding digests, then remove only that stale lock. The Rust outbox remains authoritative; do not delete its unknown transactions.

`queryFinality.payload={digest}` returns `known:false` for an unknown digest or confirmed effects/events/checkpoint and raw `gasUsed`. Finalized failure is distinct from unknown. `queryOrder` takes `orderObjectId` or `orderId`, reads Dubhe's real registry and order bag through the fullnode, and returns `status` plus canonical fields. The adapter decodes objects, dynamic fields and business events from BCS, avoiding incompatible JSON renderings between RPC versions. `replayEvents` defaults to GraphQL filtering by this package's `procurement_system` transaction module and deployment checkpoint. It returns at most 50 raw edges per page, ignores internal field-write noise and emits relevant Created/Transition/Fence wakeups. Every emitted event carries an opaque `{graphql:edgeCursor}`; page `nextCursor` has the same shape. Persist each processed event ID and its cursor in the same transaction, then persist page progress including empty pages. Legacy checkpoint cursors restart from the deployment bound and rely on inbox deduplication. GraphQL lag/failure/forgery cannot authorize delivery: finalized gRPC transaction effects and a fresh coherent fullnode order read remain mandatory. The general Dubhe indexer's gRPC notification can precede its SQL commit and is also only a wakeup.

`eventReplayMode:"checkpoint"` explicitly enables the small-localnet/dedicated-fullnode fallback, scanning at most 32 checkpoints with eight concurrent reads while emitting in ledger order. Each event then carries `{checkpoint,transactionIndex,eventIndex}` pointing after that event. Public testnet whole-chain scanning was measured to lag or barely match chain growth and is not the default listener. Public GraphQL is suitable for development; production needs a suitable provider or operated indexer with defined retention and availability. Neither index route replaces per-order active reconciliation.

Compensation observations read the finalized Clock **first**, then the complete object/bag, then re-read the parent object version and previous transaction. A concurrent version change or missing matching finalized effects/event rejects the observation. `observation.clock` identifies the fresh observation; `observation.transactionDigest` separately identifies the order's last mutation. An unchanged order with a later Clock is a distinct reconciliation observation and must not collide in the owner's inbox. A stable registry absence is returned separately with `registryAbsence:true`; it is never a fabricated cancel receipt, and only permits refund once every issued publish proof is definitively expired or revoked.

This read consistency requires one trusted, consistent fullnode or a sticky endpoint. Do not use a proxy that can mix stale replicas between these reads. RPC responses are not a cryptographic light-client snapshot proof; the test endpoint must be validated before enabling compensation. `config.enabled` enables this adapter and its explicit credentials, not new NPC publication. Closing publication must leave the recovery worker and old-order reads enabled.

## Validation and cost reporting

`npm ci --ignore-scripts` and `npm test` run isolated Node tests. Use the pinned Sui toolchain for `sui move build/test --path src/mir2_procurement --build-env testnet`. Before invoking the CLI, set `SUI_CONFIG_DIR` to a dedicated external directory containing a testnet `client.yaml` and an empty `[]` keystore, with no active address. The official CLI may otherwise initialize a missing default wallet even for `move build`. No Docker or local node is needed. Actual testnet deployment requires separately authorized isolated test keys, faucet test tokens, verified framework/DApp IDs and explicit gas limits; never reuse the user's default wallet. Deterministic fixture keys are public test vectors and must never be deployed.

`scripts/testnet-lifecycle.mjs --run-isolated-testnet` is an explicitly invoked development harness, separate from the default-disabled worker. Set absolute external `MIR2_PROCUREMENT_TEST_ROOT` and `MIR2_PROCUREMENT_TEST_BYTECODE` paths; only the first run may set `MIR2_PROCUREMENT_ALLOW_ISOLATED_TEST_KEYS=1`. Restrict its private directory to the current operator and SYSTEM before running. It preserves exact signed bytes before submission and receipts after finality. The public faucet now requires v3 Argon2d proof-of-work; its helper verifies the official conformance vector and saves the exact proof/result so unknown outcomes do not request another payout. Its setup budgets total at most 1.02 test SUI and its shared runtime ledger allows at most 0.98, for a total maximum of 2 test SUI. The runner's asset-lock records are fixtures; its chain success is not proof of game database delivery.

Expected happy-path calls from this implementation: publish 2; publish+fill 3; publish+cancel 3; publish+expire 3; a revocation adds 1. These are **code-path counts, not measured network results**. Gas must be reported from actual receipts, separating computation/storage/rebate and one-time deploy/genesis costs. USD conversion, profitability and the suggested $0.10 service price are unverified. Server database, RPC and optional indexer costs must be reported separately. No real service charging is enabled here.

The [2026-10-28 validation record](validation/20261028/README.md) contains 14 passing Move tests, 21 passing Node tests and three actual testnet order lifecycles with all nine transactions finalized. It reports measured Gas separately from these expected code paths. The chain lifecycle used custody fixtures; Windows and real game-database delivery are a separate acceptance gate.
