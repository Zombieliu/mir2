# Repository large-file policy

The Git repository contains source, deterministic configuration, compact manifests, and reviewed summaries. It does not retain reproducible runtime binaries or run-specific QA captures in the current tree.

## Kept outside Git

The following paths are generated and must be published as CI artifacts or immutable object-storage/release assets:

- `apps/web/public/bevy-runtime/`: fetched from the production R2 release and verified against `apps/web/lib/generated/bevy_runtime_version.json`.
- `docs/generated/player-qa/`: browser reports, screenshots, timelines, and runtime logs.
- `docs/generated/packet-traces/`: packet captures and comparison matrices.
- `docs/stage2-screenshots/` and `docs/stage5-screenshots/`: bulk UI capture sets.

`node scripts/summarize-qa-evidence.mjs` writes a content inventory with a SHA-256 for every file and a deterministic aggregate digest. The Candidate GitHub Actions workflow uploads that inventory and all evidence generated by the run as the `mir2-candidate-evidence` artifact. Artifact retention is intentionally bounded; promoted evidence must be copied to an immutable R2 prefix or attached to a GitHub Release before expiry.

## Kept in Git

Keep small, reviewed Markdown conclusions, release identities, content hashes, source/configuration data, and the generated Bevy runtime version manifest. A committed document may link to external evidence, but must include its immutable version or digest and must not depend on a mutable `latest` URL.

## Release and recovery gates

1. Build Bevy WebGPU and WebGL2 from the pinned Rust source.
2. Publish both packages under `bevy-runtime/v/<runtime-version>/` in a new immutable R2 asset release.
3. Update and commit `bevy_runtime_version.json` and `config/production-web-assets.json` only after remote probes and hashes pass.
4. Run `npm run runtime:fetch:prebuilt` from `apps/web` in a clean tree to prove the repository no longer supplies the binaries.
5. Before any history rewrite, archive the evidence paths from the pre-rewrite commit, publish the archive outside Git objects, and record its SHA-256 in the rewrite runbook.

The Phase 1 deletion commit remains recoverable from its parent commit. Rewriting remote history is a separate Phase 2 operation requiring an explicit maintenance window, protected-branch coordination, a fresh-clone rehearsal, and force-push approval.
